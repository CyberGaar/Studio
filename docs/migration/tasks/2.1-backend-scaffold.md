## Acceptance criteria

- Node and npm versions match the repository pins, dependencies are exact-pinned, and the lockfile supports deterministic `npm ci`.
- Lint and TypeScript compilation fail normally; there are no `|| true`, blanket rule suppressions, or ignored build errors.
- Native tests are explicitly enumerated, cannot silently discover zero tests, and enforce at least 70% line, branch, and function coverage.
- The service starts without databases, identity, Redis, queues, object storage, policy, AI, or any other CyberGaar service.
- Every request receives a structured `503 FEATURE_UNAVAILABLE` response with no demo or cross-tenant data.
- The container uses the pinned Node runtime, runs as a non-root user, contains compiled runtime files only, and is smoke-tested read-only with dropped capabilities.
- Secret, disclosure, SPDX, SAST, dependency, allowlist, and clean-room gates pass before push.

Task 2.1 does not complete an application feature or service milestone. Feature-branch deployment and Nuclei begin when Task 2.3 provides the authenticated backend milestone.

## Security review boundaries

- No authentication or authorization claim is made by this scaffold.
- No customer, user, tenant, demo, or synthetic application records are returned.
- Request bodies are neither read nor logged.
- The only output is a fixed public-safe unavailable response and a startup line containing host and port.
- Production dependencies are empty; development dependencies are exact-pinned and audited.
